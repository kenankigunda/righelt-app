## Unit Tests

### U-01 — `collectRemovedPieceNotices`: no-retreat removal
- **Module**: `packages/api-handler/src/shell-live-core.ts` (and parallel `apps/web/shell/optimistic-live.js`)
- **Spec**: §5.1, AC4
- Drive a `before` state where a piece has `pushed: true`; verify the notice has `reason: "no_retreat"`, correct `position`, and `ownerSeat` matching `piece.owner`.

### U-02 — `collectRemovedPieceNotices`: loss-of-supply removal
- **Module**: same as U-01
- **Spec**: §5.1, AC4
- Drive a `before` state where a unit loses supply during stability resolution (present in `afterApply.pieces` but absent from `afterStability.pieces`); verify `reason: "loss_of_supply"` and correct `ownerSeat`.

### U-03 — `collectRemovedPieceNotices`: commander-unsupplied reason
- **Module**: same as U-01
- **Spec**: §5.1, AC4
- Supply a `before` state containing a Commander piece; `afterStability` has terminal outcome status (`p1_win`, `p2_win`, or `draw`) and that Commander is absent; verify `reason: "commander_unsupplied"` and `ownerSeat`.

### U-04 — `collectRemovedPieceNotices`: draw — both Commanders removed
- **Module**: same as U-01
- **Spec**: §4.4, AC3
- Both Commanders absent from `afterStability` with `draw` outcome; verify two notices returned, one per Commander, each with `reason: "commander_unsupplied"`, distinct `ownerSeat` values (`"p1"` and `"p2"`).

### U-05 — `collectRemovedPieceNotices`: multiple units in same resolution
- **Module**: same as U-01
- **Spec**: §4.3, AC1
- Multiple units removed in a single stability pass; verify one notice per piece, `position` reflects pre-removal coordinates, ordering follows engine resolution order (RIGHELT_RULES_SPEC §7).

### U-06 — `collectRemovedPieceNotices`: no removal produces empty array
- **Module**: same as U-01
- **Spec**: §4.1
- Move with no piece removals; verify empty array returned.

### U-07 — `MoveEntry` type: `destroyedPieces` field present and optional
- **Module**: `packages/api-handler/src/shell-live-core.ts`
- **Spec**: §5.1, AC8
- TypeScript compile check: `MoveEntry` accepts `destroyedPieces?: DestroyedPieceRecord[]`; missing field is valid (no compilation error).

### U-08 — normalization: missing `destroyedPieces` defaults to `[]`
- **Module**: `packages/api-handler/src/shell-live-db.ts`
- **Spec**: §5.3, AC8
- Feed `normalizeMoves` a raw move array without `destroyedPieces` field; assert each normalized move has `destroyedPieces: []`.

### U-09 — normalization: existing `destroyedPieces` is preserved
- **Module**: `packages/api-handler/src/shell-live-db.ts`
- **Spec**: §5.3, AC8
- Feed a raw move that already has a valid `destroyedPieces` array; assert normalization preserves it exactly.

### U-10 — board runtime: `setDestructionHighlight` sets position; `clearDestructionHighlight` clears it
- **Module**: `apps/web/board/runtime/board-runtime.js`
- **Spec**: §6, AC6
- Call `setDestructionHighlight({row: 3, col: 4})`; assert internal state holds the highlight coordinate. Call `clearDestructionHighlight()`; assert state is null.

### U-11 — board runtime: `loadSnapshot` clears destruction highlight
- **Module**: `apps/web/board/runtime/board-runtime.js`
- **Spec**: §6, AC6
- Set highlight, then call `loadSnapshot`; assert highlight is cleared after the call.

### U-12 — board runtime: highlight does not mutate snapshot state
- **Module**: `apps/web/board/runtime/board-runtime.js`
- **Spec**: §6, AC6, AC9
- Set highlight, call `getState()`; verify the returned state is unchanged (no extra field or mutation introduced by the highlight overlay).

### U-13 — shell render: `renderTurnHistory` emits sub-bullets for moves with `destroyedPieces`
- **Module**: `apps/web/shell/app.js` (unit-testable render function)
- **Spec**: §4.1–§4.3, AC1, AC2
- Pass a mock game with one move having `destroyedPieces: [{position:{row:2,col:3}, ownerSeat:"p1", reason:"no_retreat"}]`; assert rendered HTML contains a sub-bullet with `DESTROYED (2,3)`, the P1 color class, `data-action="jump-destruction"`, `data-move-index`, `data-position-row="2"`, `data-position-col="3"`.

### U-14 — shell render: no sub-bullets when `destroyedPieces` is empty or absent
- **Module**: `apps/web/shell/app.js`
- **Spec**: §7.1, AC13
- Move with `destroyedPieces: []` or no field; assert no sub-bullet elements in rendered output and parent `<li>` height is not reserved.

### U-15 — shell render: P2-owned piece gets P2 color class
- **Module**: `apps/web/shell/app.js`
- **Spec**: §4.4, AC2
- `ownerSeat: "p2"` produces P2 tone class on sub-bullet, not P1 class.

### U-16 — shell render: draw renders two sub-bullets with correct owner colors
- **Module**: `apps/web/shell/app.js`
- **Spec**: §4.4, AC3
- Two entries in `destroyedPieces` with `ownerSeat: "p1"` and `ownerSeat: "p2"`; assert two sub-bullets rendered, each with the correct tone class.

### U-17 — optimistic-live.js and shell-live-core.ts produce identical results for identical inputs
- **Modules**: both parallel implementations
- **Spec**: §5.1 (parity invariant)
- Smoke-check identical `(before, afterApply, afterStability, action)` tuples against both functions; assert equal outputs. Regression guard against future divergence.

## Integration Tests

### I-01 — `recordClientMove` stores `destroyedPieces` on `MoveEntry`
- **Boundary**: `shell-live-core.ts` `recordClientMove` → `game.moves[]`
- **Spec**: §5.1, §5.3, AC8
- Execute a move that causes a `no_retreat` removal via `recordClientMove`; read back `game.moves[last].destroyedPieces`; assert array has one entry with correct `position`, `ownerSeat`, and `reason`.

### I-02 — `recordClientMove` stores `destroyedPieces` for loss-of-supply
- **Boundary**: same as I-01
- **Spec**: §5.1, AC4, AC8
- Use a game state where move triggers supply disruption; verify `loss_of_supply` entry on stored move.

### I-03 — `recordClientMove` stores `commander_unsupplied` for terminal Commander removal
- **Boundary**: same as I-01
- **Spec**: §5.1, AC4, AC8
- Use a game state where move causes a Commander to be unsupplied (win condition); verify `reason: "commander_unsupplied"` on stored move and that `game.board.state.outcome.status !== "ongoing"`.

### I-04 — `recordClientMove` stores both Commander records for a draw
- **Boundary**: same as I-01
- **Spec**: §4.4, AC3, AC8
- Drive simultaneous Commander removal (draw); verify two `destroyedPieces` entries on the move record, one per Commander owner.

### I-05 — Move API response includes `destroyedPieces` (live path)
- **Boundary**: `game-room-do.ts` move handler → HTTP response body
- **Spec**: §5.1, AC7, AC11
- Submit a destructive move via the API; assert response JSON contains `move.destroyedPieces` with correct entries.

### I-06 — Move API response includes `destroyedPieces: []` for duplicate move
- **Boundary**: `game-room-do.ts` duplicate-move path
- **Spec**: §5.3
- Replay a known move; assert `destroyedPieces: []` in the duplicate response (no error, no crash).

### I-07 — History endpoint includes `destroyedPieces` per move
- **Boundary**: history API endpoint → client
- **Spec**: §5.3, AC8
- Record a destructive move; fetch the history endpoint; assert `moves[*].destroyedPieces` contains the correct records.

### I-08 — Reload: `destroyedPieces` survives game-state round-trip
- **Boundary**: persist → normalize → serve
- **Spec**: §5.3, AC8
- Record a destructive move; serialize and re-normalize the `LiveGame`; assert `destroyedPieces` on the move survives the round-trip unchanged.

### I-09 — Late-join participant receives `destroyedPieces` in history catchup
- **Boundary**: transport → store → view model
- **Spec**: §7.4, AC7, AC8
- Game with destruction moves already recorded; simulate a new participant loading game state; assert `moves[*].destroyedPieces` present in the view model delivered to the late joiner.

### I-10 — `removedPieces` (transient, §12.3) path is unchanged
- **Boundary**: `game-room-do.ts` → board runtime
- **Spec**: §5.2, AC10
- After adding `destroyedPieces`, verify the existing `removedPieces` field still flows through the response correctly and `showRemovalEffects` in the board is still called with it.

### I-11 — Optimistic move response includes `destroyedPieces`
- **Boundary**: `optimistic-live.js` → shell response
- **Spec**: §5.1, AC11
- The optimistic path must also produce `destroyedPieces` so sub-bullets can appear immediately without waiting for the authoritative response. Verify optimistic result carries the field.

### I-12 — Multi-client: P1 and P2 both receive identical `destroyedPieces` in their game snapshots
- **Boundary**: transport broadcast → both client view models
- **Spec**: AC7
- Simulate two connected clients; record a destructive move from P1; assert P2's game snapshot update contains identical `destroyedPieces` to P1's.

### I-13 — History panel rendering integration: sub-bullets appear in the rendered game panel
- **Boundary**: shell store → `renderHistoryPanel` → DOM
- **Spec**: AC1, AC11
- Drive store with a game containing moves with `destroyedPieces`; trigger render; assert sub-bullet elements present in the history list DOM.

### I-14 — `jump-destruction` click navigates to correct `moveIndex` snapshot
- **Boundary**: shell click handler → `transport.selectHistoryMove` → board `loadSnapshot`
- **Spec**: AC5
- Simulate click on a sub-bullet with `data-move-index="3"`; assert `selectHistoryMove` called with `moveIndex: 3`; assert board runtime `loadSnapshot` called with the move-3 snapshot, not a different state.

### I-15 — `jump-destruction` click triggers `setDestructionHighlight` with correct position
- **Boundary**: shell click handler → `boardRuntime.setDestructionHighlight`
- **Spec**: AC6
- Sub-bullet with `data-position-row="2"` `data-position-col="5"`; simulate click; assert `setDestructionHighlight({row:2, col:5})` called.

### I-16 — Returning to live clears destruction highlight
- **Boundary**: `return-live` action handler → `boardRuntime.clearDestructionHighlight`
- **Spec**: AC6 (implicit — highlight must not persist after leaving history mode)
- Simulate return-to-live after a sub-bullet click; assert `clearDestructionHighlight()` called.

### I-17 — Jumping to a different history item (non-sub-bullet) clears prior highlight
- **Boundary**: `jump-history` handler → `clearDestructionHighlight`
- **Spec**: AC6
- Set highlight via sub-bullet click; then click a plain `jump-history` item; assert highlight cleared before or during the new snapshot load.

### I-18 — New move appended while client is pinned to earlier history: sub-bullets appear without navigation
- **Boundary**: live-sync append → `renderHistoryPanel` update
- **Spec**: AC12
- Client pinned to move index 2; new destructive move arrives (index 3); assert move 3 and its sub-bullets are present in the panel but `game.historyIndex` remains 2 and the board shows move-2 snapshot.

### I-19 — Schema normalization mismatch logging: `destroyedPieces` absence is logged but not fatal
- **Boundary**: `shell-live-db.ts` normalization mismatch pipeline
- **Spec**: §5.3
- Feed a game with moves missing `destroyedPieces`; assert a mismatch entry is recorded (matching existing normalization mismatch pattern) and the game continues loading cleanly.

## E2E Tests

- **Workflow**: Core multiplayer (History navigation row)
- **Spec**: AC1, AC2, AC4, AC7, AC11
- Two-player game; execute a move that causes a `no_retreat` removal; assert history panel shows `DESTROYED (x,y)` sub-bullet beneath that move entry with correct owner color; sub-bullet appears at the same time as the parent move row (not after a delay).

### E-02 — Success path: click sub-bullet highlights named square on board
- **Workflow**: History navigation
- **Spec**: AC5, AC6, AC14
- Click a destruction sub-bullet; assert board shows the parent move's post-resolution snapshot; assert the named `(x,y)` square is visually highlighted; assert the interaction is one continuous motion (no second animation delay after release).

### E-03 — Persistence: destruction records survive page reload
- **Workflow**: Identity and role persistence across reload
- **Spec**: AC8

- **Workflow**: History navigation
- **Spec**: AC13, §7.1

### E-06 — Draw: both Commander sub-bullets appear
- **Workflow**: Win/end-game
- **Spec**: AC3

## Coverage Notes

- **History navigation workflow** (`WORKFLOW_COVERAGE.md`): Success E2E `present`, Recovery E2E `present`, Integration `present`. This feature is a sub-feature of that surface. E-01 through E-05 expand the existing success E2E; I-18 covers the pinned-client live-append integration variant already tracked.
- **`destroyedPieces` parity between `shell-live-core.ts` and `optimistic-live.js`**: U-17 and I-10/I-11 are the primary guards against drift between these two parallel implementations — they should be considered high-priority.
- **Pre-deploy moves**: No sub-bullets for moves recorded before this deploy (accepted, Option B). Tests I-08 and I-19 confirm the normalization default is clean and does not produce errors.
