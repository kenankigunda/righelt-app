# Testing strategy and rollout

The suite catalog in `scripts/testing/catalog.mjs` defines full validation, CI matrices, focused selection and requirement coverage. `pnpm test` runs the complete inventory. `pnpm test:plan --base origin/main` explains selection; `pnpm test:affected --base origin/main` executes it. Focused evidence is advisory. CI still runs the complete inventory on every PR, readiness transition, main push and manual run during this rollout.

Choose the lowest layer that proves a contract. Unit tests prove isolated rules. Integration proves API and subsystem contracts. Browser integration mounts production components and CSS with controlled boundaries to prove focus, geometry, accessibility, motion and delayed response handling. Real-stack E2E retains all existing account, persistence, cross-tab, multiplayer, result and recovery cases in the existing browser matrix. Responsive evidence and report usability remain independent checks.

General and account E2E run two shards for each existing browser project. Each CI job owns a fresh stack, temporary database, secrets and output directory. Real-stack workers remain one. Browser integration uses two workers and independent pages. Local full runs are sequential to avoid shared loopback ports. Account and cutover files with destructive controls run in a dedicated auth-controls lane. Tests restore maintenance controls in teardown. Each browser lane starts a fresh database, so permanent cutover cannot leak into ordinary account journeys. No blanket retry or quarantine grants a pass. Unexpected fixture process exit writes a first-cause marker and makes the receipt incomplete.

`Full validation` requires every catalog lane once, a passed receipt, matching tested source and suite catalog, compatible runtime/dependency identities and completed test observations. Missing shards, stale receipts, interrupted stacks, empty test runs, retries that conceal a failure and mismatched state modes fail the gate. Retained-state upgrade evidence remains separate and is not replaced by fresh-stack receipts. The candidate harness imports explicit suite receipts from immutable CI artifacts, verifies their primary logs and binds credit to the requested command and exact runtime/dependencies. The pinned released harness remains unchanged until this change is merged and explicitly installed.

Performance observations use real clocks and preserve raw navigation and dialog-paint samples. They do not introduce arbitrary latency thresholds. Existing recovery/payload assertions remain authoritative. Unsupported or missing measurements cannot be treated as passing observations. Collect same-revision cold runs and fault runs before setting budgets or reducing browser coverage.

Roll out in stages: first review the generated CI matrix and mutation tests; then compare full local and hosted runs at the same revision; investigate each failure from primary evidence. Only enable focused draft CI after indirect dependencies, API response drift, UI focus/layout/motion faults, auth authority regressions, killed fixtures, missing shards and stale receipts have been shown to select or fail correctly. Keep full validation required on ready PRs and main. After merge, configure branch protection to require the uniquely named Full validation check, and install the merged validation-tools release explicitly. Neither branch rules, deployment activation nor the pinned released installation is changed by this development branch.

Regenerate CI with `node scripts/testing/workflow.mjs`; check drift with `node scripts/testing/workflow.mjs --check`. The JSON document in ci.yml is valid YAML and avoids a second handwritten inventory. Suite receipts and raw logs are uploaded even on failure. Superseded PR runs are cancelled; main runs are not cancelled. Automatic deployment continues to require a successful complete CI run on main.
