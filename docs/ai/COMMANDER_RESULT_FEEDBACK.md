# Commander defeat and result feedback

A commander removed by a push must be reported as destroyed. An existing commander without supply keeps the supply-loss reason. The engine and browser runtime share the outcome classifier. Existing persisted games are interpreted from their terminal pieces when their old reason is ambiguous, without changing any saved game, move, receipt, model or training data.

Seated players see “You won” or “Your opponent won” as the main heading, with commander explanations phrased from their perspective. Spectators see the winning player, such as “Player 1 wins”. The player's established side determines victory or defeat feedback. Spectators and computer-versus-computer games remain neutral. Self-play keeps the selected starting-side perspective. Draws remain neutral outcomes for both sides.

The commander emblem and cut stones use the authoritative winner's actual player color, red for Player 1 and blue for Player 2, including throughout the victory animation. On victory, Review game and Play again match that image color and use the existing corresponding hover and pressed palette. This affiliation stays within the result surface. The rematch dialog retains its opposite-side default and independent colors. The next turn, rematch side and default affiliation do not choose the result color. An observed live victory has one finite rising-and-settling effect. Defeat has a quieter settling effect. Reduced motion keeps the static emblem. Repaints retain elapsed animation time. Initial hydration, reload, history and manually opening a result never start an effect. Navigation, backgrounding and account/storage changes cancel it. Sound uses existing mute, focus and visibility preferences, with distinct brief rising and soft falling cues only after confirmed live completion.

Validation covers actual no-retreat commander removal through its legal continuation, genuine loss of supply, mixed draw causes, generated-runtime parity, saved legacy results, perspective, finite animation ownership and confirmed sound. Real result workflows verify history/reload/manual opening and reachable actions at narrow and landscape sizes. This release preserves the deployed rematch selector. Later board UX integration must retain its native opponent cards alongside this result behavior.

Archived training decisions include the complete terminal state in their hashes, including its reason. The trainer replay verifier first requires the current exact hash. For a newly classified destruction outcome only, it may instead compare a clone with the original unsupplied reason against the archived exact hash. The same guard applies to the exact initial-state hash after a retained warmup, including accepted terminal archives with no decisions. The canonical classifier must confirm the same status and destruction cause. Every piece, board flag, turn field, continuation and other outcome field still participates in the hash. On a match, the replay keeps that historical reason in its temporary state so the unchanged archive final hash and training inventory remain verifiable. It never rewrites a record, model provenance, global hash function or engine state. This compatibility path remains necessary while these retained training records exist. New games always record the corrected cause.

All production games and complete move history must remain preserved as training data unless the user explicitly authorizes deletion, including synthetic smoke games. This work authorizes no hosted deletion, retention cleanup, reset, account activation or destructive migration. Local process cleanup is permitted. Evidence publication and schedules stay paused. Merge follows the ordered UX releases and requires the lead's coordinated slot.
